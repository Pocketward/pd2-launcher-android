# Our patches for the mali-panvk tree

Applied by `build-mali-panvk.sh`, in name order and exactly (`--fuzz=0`, no offset), to the mali-panvk tree that `config.sh` pins (`MALI_PANVK_COMMIT`), after the WSI series of `../radv-xclipse/`. The tree changes only through these patches. The app uses this driver on every Mali that the tree knows (the mali-panvk route, `MaliPanvk.kt`): the job-manager (JM) Malis, Bifrost v6/v7 and Valhall v9, and the CSF Malis, v10 to v13 (ADR 0031); our own PanVK (`../mesa-panvk/`, `../../mesa-kbase/`) drives a CSF Mali only where this route cannot run. A debug build can force this driver on any Mali (`debug/system-driver-mali-panvk`). The patches carry fixes of our own PanVK that the tree does not have, fixes for the tree's job-manager path, and what older CSF kernels need. The sizes are `git apply --numstat`'s, with blank lines.

- `0001-panfrost-model-mali-g710.patch` (+2): `../mesa-panvk/0006` for the tree (the same entry, 4 lines lower): a `pan_model_list` entry for the Mali-G710 (product id 10.8.2), with the G610's values. Without it PanVK refuses the G710 (the tree's v9 fallback by product major does not apply to v10). A CSF GPU: nothing on JM.
- `0002-panfrost-crc-clear-colour-hash.patch` (+25/-8): `../mesa-panvk/0004`, unchanged (the tree's `pan_desc.h` is its Mesa base's): a 64-bit mixing hash for the CRC clear colour, so different clear values do not collide and transaction elimination does not skip a clear. Built for every arch from v7, so it reaches the JM GPUs of v7 and v9 too.
- `0003-panvk-kbase-csf-set-event-signals-the-kernel.patch` (+20): the `vkSetEvent` part of `../mesa-panvk/0002` with the notify op of `../../mesa-kbase/` (`kbase_kmod_notify_sync_update`), for the tree's kbase backend: `pan_kmod_kbase_csf_event_signal()` (`KBASE_IOCTL_CS_EVENT_SIGNAL`, ioctl 44; nothing on JM), called by the CSF `vkSetEvent` after its write, so kbase evaluates the wait of a queue group that it suspended on the event. Without it a GPU wait on a host-set VkEvent does not end.
- `0004-panfrost-kmod-kbase-dmabuf-size-from-the-import.patch` (+7/-7): the tree's kbase backend sizes an imported dma-buf by `lseek` and refuses it when `lseek` gives 0 or less ("kbase: invalid dmabuf size"). The size is now what `KBASE_IOCTL_MEM_IMPORT` answers (`va_pages`), as in `../../mesa-kbase/` (`kbase_kmod_bo_import`); the `lseek` answer only checks it when there is one.
- `0005-panvk-kbase-jm-gpu-fault-is-a-lost-device.patch` (+21/-3): on JM, a submission that did not complete (a GPU fault) marks the queue lost (`vk_queue_set_lost`): in the done callback before its signals, in the blocking path, and in a new callback for the parts of a submission too large for one JOB_SUBMIT. The fence wait, the next submit and `vkQueueWaitIdle` then answer `VK_ERROR_DEVICE_LOST`, not `VK_SUCCESS`. An error of a fence-trigger atom (no GPU work) never fails a submission.
- `0006-panvk-kbase-jm-device-end-with-a-time-limit.patch` (+77/-12): the JM queue's waits for idle and for the device's end have a time limit. `vkQueueWaitIdle` waits up to 10 s (longer than kbase's own job time-out), then the device is lost. `destroy_gpu_queue` waits up to 10 s, then abandons the work still in flight (`pan_kmod_kbase_abandon`) and logs the queue's state and each atom still in flight ("kbase: atom N (submission S) has not reported"). The event thread then waits 2 s for the atoms still in flight and logs each one ("kbase: atom N (submission S) never reported"). Patch 0009 changes how the abandoned work ends, which waits have the limit, and from when it counts.
- `0007-panfrost-kmod-kbase-jm-open-submissions-fit-their-table.patch` (+3/-1): the tree's JM submission keeps each open submission in `open_seq[256]` until its callback has run, but frees its atom numbers before that, so more than 256 can be open, and the table overflows into the queue's counters (then a wait for idle can go on for ever). A submission also waits for room in the table.
- `0008-panvk-kbase-jm-callback-keeps-what-it-needs.patch` (+71/-15): once the device is lost (0005, 0006, or another path of the tree), the app's waits answer `VK_ERROR_DEVICE_LOST`, and the app can free the command buffers and VkEvents of submissions that report later, which their callback reads in the tree (`panvk_kbase_report_faults`, `panvk_signal_event_syncobjs`). A submission takes the sync objects of its `vkCmdSetEvent` and `vkCmdResetEvent` at submit; the callback reads the command buffers (the fault report and its log line "panvk: the kbase submission did not complete") only while the device is not lost yet, for the first failure only, and the blocking path and the callback for a part of a large submission log that line in the same way. A sync object's handle carries a generation above the table's index, so a freed handle stays refused when its slot holds a new object.
- `0009-panvk-kmod-kbase-jm-abandoned-work-ends-as-failed.patch` (+189/-65): `pan_kmod_kbase_abandon` ends the work still in flight as failed (each callback runs once, with ok false, so its sync objects are signaled, and then the work is no longer open, so every wait for it returns; a blocking submitter's work stays open until its callback has run), and from then on nothing is submitted. Every wait of panvk for submitted work on JM has the limit (`panvk_kbase_wait_seq`: `vkQueueWaitIdle`, the queue's destroy, a command buffer used again, the BC refresh ring, an emulated BC image), and so does a submission's wait for free atoms, for room in `open_seq` or for the work before it: when the work sends no event for 10 s (1 s on a device that is lost already), the device is lost, and the work is abandoned. Such a wait of panvk logs "panvk: the queue's work did not report in N s"; a submission's wait logs "kbase: the queue's work sent no event in N s", and then the submission is not sent. The limits count from the last event of the work, so a long queue of valid work is not a lost device. The log names the oldest open submission.
- `0010-wsi-x11-direct-present-records-its-blit-for-each-present.patch` (+14): the direct present (`../radv-xclipse/0004`) records its blit (a swapchain image into one of the app's buffers) again for each present: it frees the chosen pair's command buffers and records them again before it submits them, because a draw command buffer submitted a second time faults on the job manager. The image's last blit has completed then: the image comes back only after the WSI waited for it.
- `0011-wsi-x11-direct-present-imports-the-dma-buf-fd.patch` (+16/-4): the direct present imports the first fd of a buffer's handle that is as large as the picture (by `lseek`), else the first: a MediaTek gralloc's handle starts with an fd that is no dma-buf (`anon_inode:gralloc_extra`), and kbase refuses such an fd.
- `0012-panfrost-kmod-kbase-csf-older-group-and-tiler-heap-layouts.patch` (+91/-2): on CSF, a `CS_TILER_HEAP_INIT` or `CS_QUEUE_GROUP_CREATE` that gets ENOTTY in the newer layout is sent again in the older one (`_1_13`, `_1_6`), as `../../mesa-kbase/` does, and the device keeps the older layout. MediaTek's kbase reports a newer uAPI than its layouts: on a MediaTek Mali-G710 (r32p1, uAPI 1.18) the tiler heap request got ENOTTY, and Zink's `vkCreateDevice` failed. Nothing changes on JM.
- `0013-panfrost-kmod-kbase-csf-logs-the-kernel-interface-and-a-faulting-instruction.patch` (+62/-6): logging for the choice between the two kbase backends on CSF (issue 23). At CSF start one line: the uAPI, the firmware's interface version, the slots, and whether `MEM_JIT_INIT` and `MEM_EXEC_INIT` were accepted. A queue fault names `CS_INVALID_INSTRUCTION` (0x49), logs the faulting queue's ring positions (insert, `CS_EXTRACT`) with the instruction before `CS_EXTRACT`, and the words at the sideband address, from the ring or through `/proc/self/mem` (an address not mapped on the CPU gives a line, not a fault).
- `0014-panfrost-kmod-kbase-csf-waits-for-the-firmware-scoreboards.patch` (+5/-2): the CSF submission's closing cache clean and WAIT name every scoreboard the firmware reports (CS_FEATURES), not 16. A MediaTek G710 (firmware interface 1.1.0) has 8, and its firmware stopped the queue at the WAIT with `CS_INVALID_INSTRUCTION`.
- `0015-panfrost-kmod-kbase-executable-zone-before-jit.patch` (+7/-4): the context's executable zone (`MEM_EXEC_INIT`) before its JIT zone (`MEM_JIT_INIT`), as `../../mesa-kbase/` makes them: kbase refuses the executable zone once the context has a JIT zone (EPERM). On a MediaTek G710 (r32p1) the executable BOs then fell back to SAME_VA, and the GPU faulted at the first shader.
- `0016-panfrost-kmod-kbase-csf-queues-handle-tiler-out-of-memory.patch` (+7): the CSF queue group is made with `BASE_CSF_TILER_OOM_EXCEPTION_FLAG` in `csi_handlers`, as `../../mesa-kbase/` makes it, so kbase gives the tiler's out-of-memory exception to the handler that PanVK's command streams install (incremental rendering: a render pass drawn in parts). With the field 0, kbase grew the heap itself up to its maximum, and a render pass that needed more made the group fatal. The 1.6 layout (0012) has no such field.

Patches 0010 and 0011 change only this tree's WSI: the other drivers' WSI does not change.

JM has one more known gap, which the app accepts: a GPU wait on a VkEvent that the host sets (`vkSetEvent`) does not wait (the tree's JM submission drops the event waits). A fix needs kbase's soft-event atoms or a submit thread: not a small patch.

When `MALI_PANVK_COMMIT` moves, refresh each patch for the new tree: `build-mali-panvk.sh` refuses a patch that needs an offset or fuzz. When a fix of `../mesa-panvk/` or `../../mesa-kbase/` changes, port the change here too.
