# Mesa patches (Vulkan WSI, OpenGL)

Applied by `build-mesa.sh`, by `build-panvk.sh` before `../mesa-panvk/`, and by `build-sysdrv.sh` before `../mesa-sysdrv/` (its Venus build), to the commit of Mesa's main branch that `config.sh` pins (`MESA_*`), all exactly (`--fuzz=0`). The `*-wsi-*` patches touch only `src/vulkan/wsi`, which every Mesa Vulkan driver shares; PanVK gets only those. `build-sysdrv.sh` also applies the patches that `config.sh` names in `MESA_SYSDRV_GL_SHARED_PATCHES` (0005) to the system-driver mode's older Mesa (`MESA_SYSDRV_VERSION`), and `mesa-update.sh` checks that they still apply there. `../../mesa-update.sh` tries them on a newer commit of main and refreshes them for it; each is written against the pinned commit (no offsets).

- `0001-wsi-sw-reads-cached-memory.patch`: the software X11 present (`MESA_VK_WSI_DEBUG=sw`) reads each frame from host-cached memory, non-coherent if need be with `vkInvalidateMappedMemoryRanges` before each read, instead of write-combined memory.
- `0002-wsi-sw-present-counter.patch`: when `PD2_PRESENT_COUNTER` names a file, the software present increments its first 32-bit word once all of each frame has been sent to the X server (`xcb_flush`), which takes it in request order.
- `0003-wsi-sw-paced-by-the-game-view.patch`: the software present waits, at most 100 ms, until the Game view has taken the previous frame off the X screen (signalled in the present counter's page), in every present mode. Since 0008 the app's clock paces the game; this take stays for the X screen path only, so that Xvfb never writes a frame over one the copy is reading, until a device check shows that the path does not tear without it (then 0007 and this take can go).
- `0004-wsi-sw-direct-present-to-the-app.patch`: when `PD2_PRESENT_SOCKET` names the app's socket, the swapchain imports the app's AHardwareBuffers, blits each frame into a free one and sends `PRESENT` (with the swapchain's present mode, so the app tells vsync on from off) instead of `PutImage`; any setup failure keeps `PutImage`, and the end of the direct present shuts the socket down.
- `0005-teximage-subimage-bounds-without-overflow.patch` (`build-mesa.sh` and `build-sysdrv.sh`, not PanVK's build; it touches `src/mesa/main`): the texture sub-image bounds check adds offset and size as 64-bit numbers, so an offset near `INT_MAX` (D2GL passes one) cannot wrap to a small number and pass the check, after which the copy wrote far out of the texture.
- `0006-wsi-sw-fence-wait-in-the-present-thread.patch`: the X11 software present waits for each image's fence in its present thread, before it reads the image, instead of in `vkQueuePresentKHR`'s caller (`wsi_common_queue_present`). Zink presents from its submit thread, which then stopped until the GPU had finished the frame, so the game's work, the GPU and the copy to the X server ran one after another; with 0003's pacing a Mali-G715 at 60 Hz then mostly drew about 40 frames a second instead of about 55. As images can now be in the present queue while the GPU still uses them, the swapchain's destruction waits for the fences of the presented images (at most a second) before it frees their memory, command buffers and fences. A lost device in the present thread's fence wait stays `VK_ERROR_DEVICE_LOST` (Mesa makes any failure there `VK_ERROR_OUT_OF_DATE_KHR`).
- `0007-wsi-sw-back-pixmap.patch`: while the Game view paces (its word at byte 128 of the present counter's page is not 0), the X11 software present (the X screen path, not the direct present) writes each frame into a back pixmap in the X server, gives the image back to the game at once, and copies the pixmap into the window only after the Game view's take, outside the thread state lock: the game must never wait for the Game view's take. Before, the PutImage (the whole frame through the X socket) could start only after the take; in some runs on a Mali-G715 it took about 13 ms instead of 7 for 1616 × 720, the PutImage and the view's copy no longer fitted into one display frame, and every frame took two (about 38 frames a second instead of 55, the game waiting in acquire). A frame while the view does not pace (the app in the background) goes to the window as before, with no copy and no round trip. The pixmap is made at the first paced frame, at the swapchain's size (a resized window makes the swapchain again, and with it the pixmap), and freed after the present thread has ended; a frame of a resized or lost window stays in the pixmap and is neither copied nor counted; damaged areas are copied as they were put; the copies' errors are discarded like the PutImage's. When the server refuses the pixmap, the present works as before. The cost is one more frame in flight: from the game's present to the window about 53 ms instead of 43.
- `0008-wsi-sw-app-clock.patch`: the app's clock is the software present's vertical blank. The app counts ticks in the word at byte 256 of the present counter's page (and wakes its futex waiters) at the player's frame rate, and keeps the word at byte 320 non-zero while it ticks. Before each software present (to the app's buffers or to the X screen), the queue thread waits until a tick has come since its present before, in every present mode (FIFO and FIFO_RELAXED, vsync on; IMMEDIATE and MAILBOX, vsync off): the game shows at most one frame a tick, and a late frame goes at once. The game is then held at its acquire: while the clock ticks, an acquire waits until the game's last presented image has passed the clock (`sw_clock_acquire`; a count of the presented images that have not passed it, a futex), so at most one image waits for a tick and the frame on the screen is at most about one tick old (this present replaces no queued image, for MAILBOX too); an acquire with timeout 0 is not held. Until 2026-10-29 IMMEDIATE and MAILBOX never waited. Until 2026-10-30 the acquire waited only while no image was free: a game faster than the clock filled the present queue, and with Zink's three images a frame went to the screen about three ticks after the game drew it (issue #9). A clock that does not tick for 100 ms is not waited for again until it ticks, so a stalled app never holds the game. The direct present (0004) also asks the app for one buffer more than the swapchain's images (at most 5): the app keeps the newest frame while one is on the screen and one goes there, and the game still has a free buffer. For Detailed logging's pointer split (the app's `pointer_split.h`), while the app keeps the word at byte 384 set, the software present takes four `CLOCK_MONOTONIC` times of each frame (`sw_stamp`: the acquire gives the game the image, `vkQueuePresentKHR` queues it, the present thread's fence wait ends, its clock wait ends); a frame for the app's buffers gets a serial from the word at byte 448 (never 0), its times go into slot `serial % 16` of a ring of 16 slots of 64 bytes from byte 512 (a sequence lock: the slot's serial goes to 0, then the times, then the serial), and its `PRESENT` carries the serial in its last word (`format`, 0 before). Nothing while the word is 0; no allocation, and no system call but `clock_gettime`.
- `0009-virgl-vtest-socket-from-a-mesa-variable.patch`: the virgl driver's vtest winsys (the system-driver mode's VirGL route, `GALLIUM_DRIVER=virpipe`) also takes its socket from `MESA_VTEST_SOCKET_NAME` when `VTEST_SOCKET_NAME` is not set: the engine passes `MESA_*` variables to Wine processes, not `VTEST_*` (as `../mesa-sysdrv/0001` does for Venus).
- `0010-glx-drisw-present-counter-and-app-clock.patch`: the GLX software path (drisw, not Zink's kopper) counts each `glXSwapBuffers` in `PD2_PRESENT_COUNTER`'s first word after a round trip to the X server, as 0002 does for the Vulkan software present, and before each swap with a swap interval it waits for the app's clock as 0008 does. On this path the swap interval is always 1, so every swap waits, with vsync on or off: Mesa's GLX offers no swap control on the software path (`glxext.c` `bind_extensions` leaves `GLX_EXT_swap_control`, `GLX_MESA_swap_control` and `GLX_SGI_swap_control` out for `GLX_DRIVER_SW`; `driswCreateScreen` sets `setSwapInterval` only for kopper), so each drawable keeps `dri_get_initial_swap_interval`, 1 with Mesa's default `vblank_mode` (the engine passes no `vblank_mode` to the game), and Wine 11's X11 driver finds no swap control method and does not change it when D2GL's V-Sync off calls `wglSwapIntervalEXT(0)`. The VirGL route draws through no Vulkan WSI; with this the app sees its frames (frame rate, a game with no frame) and the player's frame rate caps it. It does not wait for the Game view's take (0003). Without the variable or the file nothing is counted, nothing waits and no round trip is made.
- `0011-virgl-vtest-winsys-without-libdrm.patch` (it changes meson files): virgl's DRM winsys (virtio-gpu), its link into the virgl driver and `drm_helper.h`'s virtio_gpu screen only where libdrm is found; our build links no libdrm (Turnip with KGSL only), and the VirGL route needs only the vtest winsys.
- `0012-virgl-vtest-frames-into-the-app-buffers.patch`: the VirGL route's frames stay on the GPU. When `PD2_PRESENT_SOCKET` and `PD2_PRESENT_COUNTER` are set and the vtest server says it can (`GET_PARAM` `VCMD_PARAM_PD2_APP_PRESENT`, 65; our server's patch `../../../devdriver/patches/virglrenderer-gl/0003`), each front-buffer flush of a whole frame sends `VCMD_PD2_APP_PRESENT` (65) with the resource and whether the app shows its buffers now (the word at byte 192, as 0004 reads it): the server blits the frame into one of the app's AHardwareBuffers and gives it to the app's present server with a fence (answer SHOWN), or the frame goes to the X screen as before (COPY: not wanted now, no free buffer in time; OFF: a missing extension or a failed step, for every later frame too). A GLX window on the software path (not kopper) names itself in `_PD2_PRESENT_WINDOW` at its first swap, as 0004's swapchain does, for x-input-relay, only with `GALLIUM_DRIVER=virpipe`. The constants are in `virgl_vtest_winsys.h`, not in `src/virtio/vtest/vtest_protocol.h`, which `../mesa-sysdrv/0004` changes (its command 64). 0010's clock wait and frame count stay.
