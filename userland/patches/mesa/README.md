# Mesa patches (Vulkan WSI, OpenGL)

Applied by `build-mesa.sh` to mesa-26.2.3 (`config.sh` pins the tarball), and by `build-panvk.sh` to PanVK's Mesa (`PANVK_MESA_*`) before `../mesa-panvk/`, both exactly (`--fuzz=0`). The `*-wsi-*` patches touch only `src/vulkan/wsi`, which every Mesa Vulkan driver shares; PanVK gets only those.

- `0001-wsi-sw-reads-cached-memory.patch`: the software X11 present (`MESA_VK_WSI_DEBUG=sw`) reads each frame from host-cached memory, non-coherent if need be with `vkInvalidateMappedMemoryRanges` before each read, instead of write-combined memory.
- `0002-wsi-sw-present-counter.patch`: when `PD2_PRESENT_COUNTER` names a file, the software present increments its first 32-bit word once all of each frame has been sent to the X server (`xcb_flush`), which takes it in request order.
- `0003-wsi-sw-paced-by-the-game-view.patch`: the software present waits, at most 100 ms, until the Game view has taken the previous frame off the X screen (signalled in the present counter's page), in every present mode.
- `0004-wsi-sw-direct-present-to-the-app.patch`: when `PD2_PRESENT_SOCKET` names the app's socket, the swapchain imports the app's AHardwareBuffers, blits each frame into a free one and sends `PRESENT` instead of `PutImage`; any setup failure keeps `PutImage`, and the end of the direct present shuts the socket down.
- `0005-teximage-subimage-bounds-without-overflow.patch` (`build-mesa.sh` only; it touches `src/mesa/main`): the texture sub-image bounds check adds offset and size as 64-bit numbers, so an offset near `INT_MAX` (D2GL passes one) cannot wrap to a small number and pass the check, after which the copy wrote far out of the texture.
- `0006-wsi-sw-fence-wait-in-the-present-thread.patch`: the X11 software present waits for each image's fence in its present thread, before it reads the image, instead of in `vkQueuePresentKHR`'s caller (`wsi_common_queue_present`). Zink presents from its submit thread, which then stopped until the GPU had finished the frame, so the game's work, the GPU and the copy to the X server ran one after another; with 0003's pacing a Mali-G715 at 60 Hz then mostly drew about 40 frames a second instead of about 55. As images can now be in the present queue while the GPU still uses them, the swapchain's destruction waits for the fences of the presented images (at most a second) before it frees their memory, command buffers and fences. A lost device in the present thread's fence wait stays `VK_ERROR_DEVICE_LOST` (Mesa makes any failure there `VK_ERROR_OUT_OF_DATE_KHR`).
- `0007-wsi-sw-back-pixmap.patch`: while the Game view paces (its word at byte 128 of the present counter's page is not 0), the X11 software present (the X screen path, not the direct present) writes each frame into a back pixmap in the X server, gives the image back to the game at once, and copies the pixmap into the window only after the Game view's take, outside the thread state lock: the game must never wait for the Game view's take. Before, the PutImage (the whole frame through the X socket) could start only after the take; in some runs on a Mali-G715 it took about 13 ms instead of 7 for 1616 × 720, the PutImage and the view's copy no longer fitted into one display frame, and every frame took two (about 38 frames a second instead of 55, the game waiting in acquire). A frame while the view does not pace (the app in the background) goes to the window as before, with no copy and no round trip. The pixmap is made at the first paced frame, at the swapchain's size (a resized window makes the swapchain again, and with it the pixmap), and freed after the present thread has ended; a frame of a resized or lost window stays in the pixmap and is neither copied nor counted; damaged areas are copied as they were put; the copies' errors are discarded like the PutImage's. When the server refuses the pixmap, the present works as before. The cost is one more frame in flight: from the game's present to the window about 53 ms instead of 43.
